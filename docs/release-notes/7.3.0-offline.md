# UI Kit React 7.3.0: offline support (release notes draft)

Status: draft for the 7.3.0 release.

## Dependency

- Offline support needs **Chat SDK JavaScript 4.3.1** or later. The peer dependency stays `^4.2.0`: the kit
  feature-detects every offline SDK member at runtime, so an app pinned to 4.2.x or 4.3.0 keeps working with
  offline off (no `ERESOLVE` on upgrade). Published 4.3.0 has the whole offline surface but not the fixes the
  kit relies on, so the kit also probes for a 4.3.1-only member and stays offline-off below that floor.
- React 7.x only. UI Kit 6.x (`legacy`) gets no offline support; turning the SDK's offline on with it is unsupported.

## Added (all optional; offline off by default)

- `UIKitSettingsBuilder.setOfflineConfig(config)` and the structural `CometChatOfflineConfig` type; `chatSDK.offline`
  in `initFromSettings` reaches the SDK unchanged.
- `CometChatUIEvent` members `ui:message/send-state-changed` (type `CometChatMessageSendState`) and
  `ui:offline/cache-reset`. Never emitted with offline off. **Adding members to the exported `CometChatEvent` union
  can break an exhaustive `switch`: add a `default`.**
- `hideOfflineNotices` prop on `CometChatMessageList` and `CometChatConversations`.
- `role` prop on `CometChatListItem` (`option` by default, or `group`).
- Offline strings in every locale, with plural forms. The list states are `users_connect_to_load`, `groups_connect_to_load`,
  `conversations_connect_to_load`, `group_members_connect_to_load`, `message_list_connect_to_load`,
  `reaction_list_connect_to_load`, `notifications_connect_to_load`, `search_connect_to_search` (the lists),
  `search_connect_to_search_messages` (the search screen) and `search_connect_to_search_subtitle`; the tappable edge
  rows reuse `message_list_connect_to_load_more` and `message_list_connect_to_load_newer`, which now both read
  "Connect to load more". In every locale the Android UI Kit also ships (all but en-gb, which is English), the text is
  the one Android uses for the same state, so the two kits read the same.
- Optional `connectToLoad` and `connectToSearch` fields on the users, groups, group members, conversations, reaction
  list, notification feed and pinned and saved messages contexts (set only with offline on). The search screen has only
  `connectToSearch`.
- CSS variables for the offline states, each falling back to today's value:
  - Message bubble: `--cometchat-message-bubble-offline-retry-color`, `-retry-font`, `-retry-focus-outline-color`,
    `-failed-icon-color`, `-failed-tint` (transparent by default).
  - Message list: `--cometchat-message-list-offline-footer-color`, `-footer-font`, `-notice-background`,
    `-notice-color`, `-notice-font`.
  - Conversations: `--cometchat-conversations-offline-notice-background`, `-notice-color`, `-notice-font`.
  - Media placeholder: `--cometchat-offline-media-unavailable-background`, `-color`, `-font`.

## Behaviour with offline on

- Cached first paint, then the server page in place, on the message list, conversation list, users, groups, group
  members, reactions, notification feed, pinned, saved, and search with filters and no keyword.
- The default message list asks the server for `hideReplies` only, so the SDK caches each page, and applies its types,
  categories and hide-deleted on the device. A `messagesRequestBuilder` you pass is sent as you built it, so those
  pages are not cached unless `hideReplies` is its only content filter.
- Own sends show "Not sent yet" until sent; failures are derived from the SDK's status (they survive a restart).
- Every own unsent or failed message (PENDING, SENDING, FAILED with any reason) offers Retry and Delete, and nothing
  that needs a server id (ruling R162 / S73, BEH-SEND-37 as rewritten on 2026-11-03). Retry or Delete on a message
  whose send is already under way changes nothing and shows a short "Sending… try again in a moment" notice.
- On reconnect the message and conversation lists make no fetch of their own; the SDK's catch-up is consumed. Two
  exceptions: a chat opened offline with nothing cached is read again once, because no read has answered for it, and a
  message list or thread edge that stopped at "Connect to load more" loads its page once by itself, after the reads in
  flight settle (older first, then newer), only while the window is unchanged and the edge is still blocked.
- A logout, user switch or cache reset clears every list; a cache reset then reloads it.
- What a list shows when a load fails (the same text in every UI Kit):
  - Rows on screen stay. Offline, the failure is silent: no error view, no `onError`. A real error calls `onError` once
    when you or your app started the load (open, pull to refresh, search, paging) and stays silent when the kit did
    (reconnect, foreground, sync).
  - Nothing on screen, offline: an icon and "Connect to load chats / users / groups / members / messages / reactions /
    notifications" (no Retry), or your own `errorView`; `onError` once. The list loads again once by itself on reconnect.
  - Nothing on screen, offline, keyword search: "Connect to search" with a second line, "Search needs an internet
    connection.", or your own `emptyView`; no `onError`. The search runs again once on reconnect. A list opened with
    only a filter (online-only users, tags, a builder without a keyword) is a plain list: it says "Connect to load ...",
    never "Connect to search".
  - The search screen follows Android. It says "Connect to search" (with the second line) when nothing is shown, no
    request failed with an error other than not-connected, and a keyword request could not reach the server, or both
    scopes failed. Searching by filter alone does not: the device answers it, and when it cannot reach the server with
    nothing saved it shows the plain empty state ("No results"), with no `onError` and no run on reconnect. When both
    scopes fail, at least one with a real error, it shows the error view and `onError`. With both scopes on screen and
    only one failing with a real error and nothing shown, it shows the plain empty state ("No results", or your own
    `emptyView`), with no `onError` and no run on reconnect; if the other scope has results they stay and the failure
    still reaches `onError`. When only one scope is on screen at all — in-chat search (`uid`/`guid`), or any filter —
    there is nothing to wait for: its real error is the error view and `onError`, exactly as with offline off.
  - Nothing on screen, online, a real error: the error view and `onError`, as today. It does not reload by itself.
  - The server answered with nothing: the empty view.
  - Nobody shows online while the connection is down, in any list or header, to screen readers as well.
- The group call's message queues like any other send.
- The Promise of `CometChatUIKit.sendTextMessage`, `sendMediaMessage` and `sendCustomMessage` answers every send, as on
  Android. A queued message does not reject it while the session is alive; it resolves when the message is sent and
  rejects on a final failure. Every removal rejects it once with `ERROR_OFFLINE_MESSAGE_DISCARDED`: a logout or
  user switch, a cache reset that loses the unsent messages, your user's Delete of the unsent row, and an outbox
  `DISCARDED` or `QUEUE_OVERFLOW`. The reason behind a removal is never the rejection's `code`, and the message the
  rejection is about is on the error as `sentMessage` (`error.message` stays a sentence). The kit shows nothing for that
  rejection (no error toast, no `onError`) and the composer does not lock, so only your own `.catch` hears of it.
  This holds for a send that has no local handle too. With offline off nothing changes.
  To tell one removal from another, read `ui:message/send-state-changed`: it carries `state: 'discarded'` with the
  `reason` behind it — `QUEUE_OVERFLOW` for a message the outbox evicted to make room, `DISCARDED` for your user's
  Delete of the unsent row and for an outbox discard. The rejection itself is the same for all of them, by design: one
  code an integrator can match on.

## Defect fixes visible with offline off

Each changes what an app with offline off sends or renders. They ship in this minor rather than in a separate patch
release.

Two listeners are now registered whatever the setting: the hub's SDK listeners, and one SDK connection listener per
mounted reactions, notification-feed, pinned, saved or search list (`useReloadOnReconnect`). With offline off their
handlers return at once and change nothing, so the only visible effect is the listener count in the SDK.

- **D1, new requests on reconnect.** A message list that is empty when the connection returns now issues
  `getConversation` and `fetchPrevious`, and shows its empty state again. Before, the re-run was dropped as stale and
  the list stayed blank (`useMessageListInit.ts`).
- **D2, a new request on reconnect.** A reconnect while the newest row has no server id (an un-acked send, or a
  streaming placeholder) now issues one `fetchNext` from the newest row that has one. Before, the catch-up was skipped
  and messages missed during the outage never loaded (`useMessageListEvents.ts`).
- **D3.** No duplicate conversation rows after paging past a conversation that received a message.
- **B4/N2, one row per send.** A fetch that brings back the server's copy of a message whose optimistic row is still
  on screen no longer leaves two rows with the same client id (`muid`): the row without a server id folds into the
  confirmed one, keeps its place, and takes the fetched copy's content. Two confirmed rows that share a `muid` are
  left alone — they are two real messages (a REST sender or another platform can reuse the id, and a resend after a
  lost acknowledgement gets a second server id under the first `muid`). This runs on every fetch, with offline on or
  off (`CometChatMessageList.reducer.ts`).
- **D4.** A `messagesRequestBuilder` passed to `CometChatMessageList` or `CometChatSavedMessages` is no longer modified.
- **Saved Messages accessibility.** A saved row is `role="group"` inside its list item, not `role="option"` outside a
  listbox, and no longer has `aria-selected`. Screen readers stop announcing it as a selectable option.

## Identifier additions (DOM, with offline on and off)

State-contract identifiers for automation: `data-cc` and `data-cc-*` on message rows (`key`, `id`, `state`, `mine`,
`CometChatMessageListView.tsx`), the row menu, conversation rows, notices, the list footer, the composer input and the
empty and error views. They carry no message text and screen readers do not read them. Existing `data-testid` and
`data-message-id` are kept. Integrators' DOM snapshot tests may change.

## Known issues (until the SDK changes)

- A thread page is saved only when it joins what is already saved for that thread: its jump anchor, or one of its
  rows, is a reply of that thread the device already holds. A jump straight into a thread that nothing is saved for is
  shown but not saved, so offline it is empty. Replies sent or received on this device are saved.
- A lost send acknowledgement can create one server-side duplicate (BEH-SEND-23). The sender's own device does not
  show that second copy and cannot delete it; the other side of the chat sees both. Deleting it needs another device,
  or the REST API.
- A device store that accepts a read and never answers it keeps the list on its loading state: the kit waits for the
  store rather than timing the read out, so nothing is shown and no error is reported until the store answers.
- A storage clear at logout that fails leaves the previous user's saved chats and messages on the device. They are
  shown again after a reload until that user's cache is cleared or replaced, so sign out and reload is not a reliable
  way to take their data off a shared device.
- Reading a chat offline clears that chat whole in the device's own saved copy, even when the kit only tells the
  server how far the user read. Until the server's copy arrives, the first paint after a restart — and the offline
  `unread` filter — show that chat as read, so messages that arrived during the outage carry no badge there. The
  badge is correct once the server answers; only the saved copy is affected.
- Missed messages can appear up to one sweep cooldown (10 s) after a quick reconnect.
- After a restart a failed message's reason may be unknown; it is offered Retry.
- A chat can stall while online when a send got no answer while connected; it resumes at the next reconnect (R94).
- Editing, reacting to or deleting an already-sent message needs a connection: no SDK queues these actions, so offline
  the action is refused and the message stays as it is. The UI now reports the failure instead of reporting a delete
  that did not happen. A queued message that has not gone out yet can still be retried or deleted offline.
- A reconnect the browser does not notice can leave a queued message on **Not sent yet**, and a list that failed its
  first load on its error view: the SDK can re-establish its session without reporting `onConnected`, which is the
  event the kit flushes and reloads on. The browser's own online event, or a reload, clears it.
- Multi-tab: one tab's rebuild can discard another tab's sends; that tab's rows update from the outbox events.
- Keyword search, message information, call logs and AI streamed replies need a connection. Call logs have no saved
  copy and keep their own error view.
- The browser cache encrypts content but not lookup metadata; downloaded media is stored unencrypted.
